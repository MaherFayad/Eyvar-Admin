# 07 · Performance

**The owner's question, verbatim:** *"is this the best we can achieve when it comes to over all
performance"*

**Verdict, up front.** **No — but it is close, and the remaining gap is four specific, measured
items, not a rewrite.** The work already done landed: the entry chunk is **1,279,268 B** (was
2.71 MB), route splitting is real across **55 chunks**, the fixture barrel is genuinely behind a
dynamic import, there is **no request waterfall** on any screen measured, the shell is not
remounted on navigation (AC-18 holds, verified by DOM node identity across eight hops), scrolling
a table is a **flawless 60 fps with zero React commits**, and a warm navigation paints rows in
**49–76 ms**.

What is left is **331,311 bytes of raw JavaScript sitting in the entry chunk that no operator
needs on first paint** — 270,412 B of English UI copy for forty screens they have not opened, and
60,943 B of mock fixture rows that ship even when `VITE_DATA_SOURCE=http`. Removing them takes the
entry from **1,093,170 → 761,902 B raw** and **303,991 → 224,499 B gzip (−26.2 %)**, measured by
stripping the exact byte ranges the sourcemap attributes to those modules and re-compressing. A
fifth item — the date picker, **51.9 % of the `DataTable` chunk that loads on thirty-five
screens** — is a smaller, cheaper, and lower-risk win than any of them.

Two things that sound like wins are **not** worth doing and are listed as such in §9: virtualising
the table (25 rows, zero dropped frames, zero commits while scrolling) and memoising the seven
unmemoised `columns` call sites (measured indistinguishable from the sixteen memoised ones).

## 0. Method

Everything below is measured on the production artefact, never the dev server, never estimated.

| | |
|---|---|
| Commit | `129a21e` (branch `feat/remediation-and-ux-phase1`, 311 modified files in tree) |
| Machine | Intel Core i5-14400F, 16 logical cores, 32 GB, Windows 11 26200 |
| Browser | Playwright 1.62.1, Chromium 151.0.7922.34, viewport 1280 × 900 |
| Node | v24.12.0 · Vite 6.4.3 |

```bash
# the two artefacts under test
npx vite build --outDir dist-perf-mock  --emptyOutDir                    # 20.46 s
VITE_DATA_SOURCE=http npx vite build --outDir dist-perf-http --emptyOutDir  # 18.06 s
VITE_MOCK_LATENCY_MS=0 npx vite build --outDir dist-perf-mock0 --emptyOutDir
# sourcemapped twins, used only for byte attribution
npx vite build --outDir dist-perf-mock-map --emptyOutDir --sourcemap
VITE_DATA_SOURCE=http npx vite build --outDir dist-perf-http-map --emptyOutDir --sourcemap

# served as the real artefact
npx vite preview --outDir dist-perf-mock  --port 4319 --strictPort   # 320 ms mock latency
npx vite preview --outDir dist-perf-mock0 --port 4320 --strictPort   # 0 ms mock latency
```

Byte attribution is not guesswork: a script decodes each chunk's sourcemap `mappings`, assigns
every generated byte to the original module that produced it, and — for the "what if we removed
X" numbers — deletes exactly those byte ranges and re-runs gzip and brotli on the remainder.

Runtime numbers come from the Performance API inside the page (`PerformanceObserver` for
`longtask`, `paint`, `largest-contentful-paint` and `event`), a `MutationObserver` for DOM churn, a
`requestAnimationFrame` loop for frame intervals, a React DevTools hook shim that counts
`onCommitFiberRoot` calls in the production build, and CDP `Profiler` for main-thread self time.
Medians of 5–7 cold loads unless stated.

**One caveat, stated once.** The app has no server, so every runtime number is measured in `mock`
mode. `mock` mode adds a deliberate **320 ms** artificial latency per request
(`src/data/config.ts`), which is on the critical path and is reported separately throughout.

## 5. The data layer at 1,200 rows

`src/data/mock/query.ts` does, in the browser, exactly what a server does: view predicate → free
text → filters → sort → paginate. The question is what it costs when the fixture array becomes an
API result set.

### 5.1 `runQuery` scaling

Driver fixtures grown by cloning (57 real rows), 200 iterations each, V8 24.12 (Node):

| Operation | 57 rows | 1,200 rows | 12,000 rows |
|---|---:|---:|---:|
| page 1, no sort, no filter | 0.001 ms | 0.017 ms | 0.052 ms |
| **sort by `name` (localeCompare)** | **2.478 ms** | **80.467 ms** | **843.722 ms** |
| sort by `rating` (numeric) | 0.027 ms | 0.219 ms | 3.401 ms |
| `q="ahm"` over 5 fields | 0.031 ms | 0.307 ms | 3.406 ms |
| `q` + 2 filters + sort by `name` | 0.955 ms | 36.923 ms | 406.573 ms |
| `computeFacets`, 8 fields | 0.128 ms | 0.548 ms | 1.931 ms |
| last page of the same sort | 2.076 ms | 81.412 ms | 899.877 ms |
| JSON size of the whole set | 61,469 B | **1,294,892 B** | 12,958,842 B |

**The answer to "what happens at 1,200".** Filtering, searching, faceting and numeric sorting all
stay under a millisecond — genuinely free. **A text sort does not: 80 ms of blocked main thread
per keystroke-settled query, and 843 ms at 12,000 rows.** Faceting, which looks like the expensive
one, is not.

But the honest answer is upstream of that: at 1,200 rows the client would first have to
**download 1.29 MB of JSON** to sort it. `Paginated<T>` exists precisely so it never does. The
client-side engine is a mock-mode implementation detail, and `src/data/clients/http.ts` sends
`page`, `pageSize`, `sort` and `filters` to the server. **Nothing in the UI has to change when the
API lands** — which is the point of the seam, and it holds.

### 5.2 The one line worth fixing anyway

`src/data/mock/query.ts:137`:

```ts
return String(a).localeCompare(String(b), ['ar', 'en'], { numeric: true, sensitivity: 'base' })
```

`String.prototype.localeCompare` with an options argument constructs a **new `Intl.Collator` on
every comparison** — `n log n` of them per sort. Measured on the same name data:

| Sorting | `localeCompare` (current) | one reused `Intl.Collator` | plain `<` `>` |
|---|---:|---:|---:|
| 57 names | 1.20 ms | 0.01 ms | 0.01 ms |
| 1,200 names | **49.52 ms** | **0.81 ms** (61×) | 0.21 ms |
| 12,000 names | **559.51 ms** | **9.87 ms** (57×) | 3.06 ms |

Hoisting one `Intl.Collator` to module scope is a one-line change with identical collation
behaviour. It saves 1.2 ms today and 49 ms the moment a fixture set grows. The same pattern is in
`computeFacets` (`query.ts:106`) and in 25 other comparators across `src/data/clients/**` — most
of those compare ids or ISO dates with no locale argument, which is the cheap path and fine.

## 6. Chart and table cost

### 6.1 recharts is lazy — except where it is not

`chart-*.js` is **345,578 B raw / 104,642 gzip / 87,887 brotli**. It is correctly absent from
`/operations/people`, `/operations/trips`, `/financials/payouts`, `/support/tickets` and
`/admin/team`.

**It is loaded on `/management/reports`, where zero charts render.** Blocking the chunk with
`ctx.route('**/assets/chart-*.js', r => r.abort())` makes the Reports screen fail to render
entirely — proof that it is a *static* dependency of the reports chunk, not a lazy one.

The cause is a barrel leak. Three files reach for a pure formatter through the components barrel:

```
src/screens/reports/AlertsView.tsx:56        import { formatMetricValue } from '@/components/metrics'
src/screens/reports/AlertRuleDialog.tsx:100  import { formatMetricValue } from '@/components/metrics'
src/screens/reports/ReportModeCanvas.tsx:60  import { formatMetricValue } from '@/components/metrics'
```

`src/components/metrics/index.ts` also exports `TrendChart`, which imports `recharts`. The
function itself lives in `src/components/metrics/formatMetric.ts` and has no chart dependency.

Cost: 104,642 gzip bytes downloaded and 29 ms of main-thread self time at CPU ×4 on the Reports
library view, for nothing.

### 6.2 Half the `DataTable` chunk is a date picker

`DataTable-*.js` is 138,744 B raw / 41,330 gzip and loads on **35 call sites across 23 screens**.

The calendar has exactly one consumer — `src/components/table/ColumnFilterControl.tsx` — and it is
only reachable after an operator opens a `date-range` column filter. A `React.lazy` boundary there

### 6.3 Is the table virtualised, and does it need to be?

Not virtualised — no virtualisation code exists anywhere in `src/components`. `DEFAULT_PAGE_SIZE`
is **25** (`src/data/types/common.ts:149`) and there is no page-size selector, so 25 is the only
value an operator ever sees.

At 25 rows: **60 fps while scrolling, 0 React commits, 0 DOM mutations, 0 long tasks, at CPU ×4**
(§3.2). Virtualising would add a dependency, break `Ctrl+F`, complicate the sticky column and the
row-actions focus-within rule, and buy nothing measurable. **Do not do it.** If a page-size
selector offering 100 or 250 ever lands, re-measure — but that is a design decision, not a
performance one.

## 9. Ranked, with numbers attached

### Worth doing

**1 — Split screen copy out of the entry chunk.**
**−270,412 B raw / −68,912 gzip / −56,377 brotli off first paint; −70.9 ms of parse+eval at CPU ×4.**
`src/i18n/dictionaries.ts` statically imports 28 `copy.ts` modules. Change it to a registry a
screen's chunk populates at module load: the copy travels with the screen that needs it, and
because the copy module is in the same chunk as the screen component, registration completes
before React renders it — so there is no window in which AC-74 could see a raw key. The shell's
own copy, the vocabulary, the command-palette copy and `components/profile/copy.ts` stay eager
(~39.6 KB). This is the single largest remaining win and it is also the largest piece of work.
**Owner: i18n-arabic-engineer, with the shell owner.**

**2 — Lazy-load the calendar out of `DataTable`.**
**−72,070 B raw / −20,492 gzip / −17,949 brotli off a chunk that loads on 35 call sites across 23
screens.** One `React.lazy` boundary in `src/components/table/ColumnFilterControl.tsx` around
`@/components/ui/calendar`. Highest value per line of change in this document.
**Owner: table-density-engineer.**

**3 — Stop `resolveReport.ts` leaking fixtures into the http build.**
**−60,943 B raw / −10,721 gzip / −8,436 brotli, and it is dead code in production.** Move
`OTHER` out of `mock/resolveReport.ts` so `clients/index.ts:607` no longer creates a static edge,
and route `clients/reports.ts` through the same `onFixturesLoaded` seam every other mock client
already uses. This is the last piece of the fixture-extraction job that is otherwise finished.
**Owner: mock-data-engineer.**

**4 — Deep-import `formatMetricValue`.**
**−104,642 gzip bytes and −29 ms of CPU at ×4 on `/management/reports`.** Change three import
lines from `@/components/metrics` to `@/components/metrics/formatMetric`. Three lines.
**Owner: frontend-engineer (reports).**

**5 — Hoist one `Intl.Collator` in `src/data/mock/query.ts`.**
**61× faster text sorts (49.52 → 0.81 ms at 1,200 rows).** Saves 1.2 ms today. One line, no
behaviour change, and it removes a cliff that only appears once a fixture set grows.
**Owner: mock-data-engineer.**

**6 — Memoise the seven unmemoised `columns` call sites (§4.3).**
**Measured benefit: zero at 25 rows.** Do it for consistency with the other sixteen and because it
is the kind of thing that stops being free if the page size ever changes — not because it is
costing anything now. Say so in the commit message.

Items 1–4 together take `/operations/people`'s first load from **502,727 B** of gzip JS to roughly
**405,000 B (−19 %)**, and the http entry from **1,093,213 → 761,902 B raw (−30.3 %)**. That is
arithmetic on independently measured parts, not a projection.

### Not worth doing

**Virtualise the table.** 25 rows a page, 60 fps at CPU ×4, zero React commits and zero DOM
mutations while scrolling (§3.2, §6.3). There is no cost to remove. It would add a dependency and
break `Ctrl+F`.

**Replace recharts.** 345,578 B is a lot, but it loads only where charts render and costs 373 ms
at CPU ×4 on a screen that draws two charts. Swapping a charting library against a design system
is a large change for a benefit that only two of forty screens would see. Re-measure if the metric
boards grow.

**Shrink or defer the Arabic font.** 94,332 B, fetched because Arabic captain names are on the
page. Real data will do the same. `unicode-range` is already correct.

**Tune the service-worker precache.** 1.15 MB of background fetch buys the offline guarantee, runs
off the main thread, and shows up in none of the runtime measurements.

**Reduce the 3.6 React commits per keystroke.** Zero long tasks unthrottled, 104 ms worst-case
event duration at CPU ×4 against a 200 ms threshold. There is nothing to win.

## 10. So: is this the best achievable?

No. **The entry chunk can lose 30.3 % of its raw bytes and 26.2 % of its compressed bytes without
one screen changing behaviour**, and the `DataTable` chunk that lands on thirty-five screens can
lose half of itself to one `React.lazy`. Those are measured, not projected.

But the architecture is right, and that is the harder half. Route splitting works — 12,183 bytes
of the 1,093,170-byte entry is screen code. There is no request waterfall on any route. The shell
survives navigation as the same DOM nodes. Warm navigation is 49–76 ms. Scrolling is a clean 60 fps
with zero React work at CPU ×4. Typing is 104 ms worst-case at CPU ×4 against a 200 ms threshold.
The client-side query engine will be replaced by `Paginated<T>` at the seam with no UI change, and
the one place it would have hurt at scale is a single line.

What remains is four leaks — a barrel, a static re-export, a static import block and an eager
calendar — each with a name, a file, a line number and a byte count.
