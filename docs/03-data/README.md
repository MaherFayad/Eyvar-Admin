# `docs/03-data/` — machine-readable export

The structured JSON representation of the original single-file prototype, generated by static
analysis of it:

```
eyvar_ops_panel_v40_fixed.html    21,857 lines    1,580,139 bytes
```

Nothing here is runtime data. No part of the panel was executed. Every fact is either read
directly out of the source file or transcribed from `docs/01-modules/*.md` and then checked
back against the source.

---

## The files

| File | What it holds | Grain |
|---|---|---|
| `system-inventory.json` | Master artefact: file metadata, navigation tree, and every module | one object per module |
| `modules-detail.json` | Full module objects, when `system-inventory.json` had to be split for size | one object per module |
| `findings-register.json` | Every defect, dead-code item, mock and risk, deduplicated, with stable ids | one object per finding |
| `entities.json` | The `DB` object as a data model — collections, fields, seed counts, relationships | one object per collection |
| `actions-catalog.json` | Flat catalog of every action in the system, plus every modal | one row per (handler, page) binding |

If `modules-detail.json` is present, `system-inventory.json` carries module *summaries* only and
`meta.split` is `true`; the full objects are in the detail file, keyed by the same `id`. The current export fits
in one file (1.3 MB), so there is no `modules-detail.json`.

Two prose companions sit alongside these, written by a separate pass and not generated by this
pipeline: **`DATA-MODEL.md`** (narrative walkthrough of the `DB` object) and **`GLOBAL-STATE.md`**
(the non-`DB` globals in the L2166–L21855 script region). `entities.json` is the machine-readable
counterpart to `DATA-MODEL.md`; where they disagree, `entities.json` was read mechanically from
the source and `DATA-MODEL.md` was written by hand.

### `findings-register.json`

```jsonc
{
  "meta": { "severity_rubric": {…}, "counts_by_severity": {…}, "counts_by_type": {…},
            "total": 0, "verified": 0, "unverified": 0 },
  "findings": [ {
    "id": "F-001",
    "type": "BUG | DEAD_CODE | MOCK | GAP | RISK | INCONSISTENCY",
    "severity": "critical | high | medium | low",
    "module": "12b-driver-wallets",   // null for findings that are not module-specific
    "title": "…",
    "detail": "…",
    "source_lines": [7058],
    "evidence": "…verbatim source quote…",   // null where none was captured
    "impact": "…",
    "doc": "docs/01-modules/12b-driver-wallets.md",
    "verified": true                   // false ⇒ the doc marked it UNVERIFIED, or it could not be confirmed in source
  } ]
}
```

**Severity rubric** — applied consistently across every finding:

| Severity | Meaning |
|---|---|
| `critical` | moves money incorrectly, loses data, or bypasses a security/permission control |
| `high` | a displayed number is wrong, or a user-facing action silently does nothing |
| `medium` | dead code, missing audit entry, inconsistent behaviour |
| `low` | cosmetic, i18n, or demo-data artefact |

Ids are assigned after sorting by severity then module then title, so `F-001` is always a
critical finding. **Ids are not stable across regenerations** — join on `title` + `module`
if you need to track a finding over time.

## How it was produced

Two passes, cross-checked against each other.

**1. Mechanical pass — the source file only.**
Node scripts parsed `eyvar_ops_panel_v40_fixed.html` directly:

- **Pages / navigation** — regex over the HTML body (L472–L2165) for `<div class="page" id="p-…">`,
  `.sb-sec-lbl` / `.sb-item` sidebar markup, and `.settings-tab` buttons.
- **The `DB` object** — a bracket-matching walker over the `var DB={…}` literal (L2566–L2842) plus
  every later `DB.x = …` assignment, yielding collection names, line spans, seed counts and id prefixes.
- **Functions** — brace matching from each `function f(` / `window.f = function`. The matcher is
  string-, template-, comment- **and regex-literal**-aware; a naive scanner desyncs on this source
  because it contains regexes holding quote characters (e.g. `/[",\n]/` in `toCSV`).
- **Per-handler facts** — within each function body: `requirePerm('…')` / `can('…')` → permission gate,
  `logAction('…')` → audit action key, `confirmAction(` → confirmation, and `DB.<x>` mutations → writes.
- **Transitive writes** — propagated up the call graph to 3 hops so a handler that delegates to a
  helper is credited with what the helper does. Traversal deliberately stops at `render*`, `go`,
  `switch*` and similar page-level functions; following those makes every handler appear to touch
  every collection.
- **Dead code** — an identifier appearing exactly once in the whole file (its own definition) has
  no call site, onclick binding or string reference.

**2. Documentation pass — `docs/01-modules/*.md`.**
The module docs are read in full and each doc's sections mapped onto the module schema, with line
numbers, page spans and handler names spot-verified against the source and an `INCONSISTENCY`
finding recorded wherever a doc's line number is wrong. Every doc on disk has a module entry.

**Merge rule.** Where the two passes disagree, the mechanical pass wins for anything structural —
line numbers, page spans, permission gates, audit keys, DB writes. The docs supply everything the
source cannot state for itself: purpose, labels, formulas, thresholds, narrative and impact.

Where a mechanical finding restated a doc-derived one about the same handler and the same concern,
the two were folded into a single entry carrying both sets of line numbers and
`"confirmed_mechanically": true`. Eight findings are marked that way — they are the ones with
independent evidence from both passes.

The extraction scripts are not in the repo. `docs/00-index/METHODOLOGY.md` records the shell
commands behind `GROUND-TRUTH-INVENTORY.md`.

## Known limits

Read these before trusting a number.

1. **Static analysis only.** The panel was never run. Anything that depends on runtime state —
   what a KPI actually renders, whether a branch is reachable with real data — is inferred.
2. **Transitive writes are a 3-hop approximation.** Traversal stops at render/navigation functions,
   so a write reached *only* through one of those is not counted. `writes_to_direct` is exact;
   `writes_to` is a lower bound with a small chance of over-reach.
3. **Entity fields come from the first seed record.** Optional fields present only on later records
   are missing, and `type` is the seed's type, not a declared schema.
4. **`seed_count` is demo data**, not production volume. The whole `DB` object is a fixture.
5. **Page attribution for JS-emitted controls and actions** is resolved through the router map
   (`go()` → render function → page). A handler emitted by a helper that several pages call gets
   attributed to the first page in the router map, and shows `page_id: null` when no route reaches it.
6. **Finding ids are not stable across regenerations.** See the note under the register's schema.
7. **`verified: false` is meaningful.** It carries through a doc's own `UNVERIFIED` marker. Do not
   treat those findings as confirmed defects.
8. **Three counts in `GROUND-TRUTH-INVENTORY.md` do not match the source.** Corrected here:
   - It reports **27** sidebar nav items and `00a` reports **31**; the source has **30**
     (`.sb-item` elements across the 9 `.sb-sec` blocks).
   - "Static `<input>` 225" is a whole-file count including controls inside JS template strings.
     Only **65** `<input>` elements sit in the static HTML body; the `origin` field distinguishes them.
   - Its Settings tab groups (Workspace / Operations / System) are the *markup* groups.
     `reorderSettingsTabs()` (L21278, called from L21393) deletes those three headers at boot and
     regroups all 21 tabs into the six `SETTINGS_GROUPS` (L21270): Daily operations, Money,
     People & access, Customer comms, Platform, Records. `navigation.settings_tabs[]` carries both —
     `static_group` for the markup and `group` for what users actually see.
9. **Coverage follows the docs.** A module with no doc has no entry. All 61 docs are
   covered by 62 modules — `05b-corporate-accounts.md` yields two, one per page it documents
   (`corporate` and `corp-detail`). List `docs/01-modules/` and diff against `modules[].doc` to
   re-check after the docs change.
10. **The same defect can appear once per module that reports it.** Deduplication keys on
   module + title, so a cross-cutting defect documented from two modules' perspectives keeps both
   entries (e.g. the double-booked cancellation refund appears under both `12a-finance` and
   `12c-rider-wallets`). Group by `title` to collapse them.

## Example queries

All examples use [`jq`](https://jqlang.github.io/jq/). Run them from the repo root.

**Every money-moving action with no permission gate** — the headline security query:

```bash
jq -r '.actions[] | select(.moves_money and .permission_gate == null)
       | "\(.handler)  L\(.line)  \(.page_id // "—")  writes \(.writes_to | join(","))"' \
   docs/03-data/actions-catalog.json
```

**Actions that mutate `DB` but never call `logAction()`:**

```bash
jq -r '.actions[] | select((.writes_to | length) > 0 and .audit_action_key == null)
       | "\(.handler)\tL\(.line)\t\(.writes_to | join(","))"' \
   docs/03-data/actions-catalog.json
```

**All critical findings, grouped by module:**

```bash
jq -r '.findings[] | select(.severity == "critical")
       | "[\(.id)] \(.module // "global"): \(.title)"' \
   docs/03-data/findings-register.json
```

**Findings the docs could not confirm** (carry the caveat forward — do not report these as defects):

```bash
jq -r '.findings[] | select(.verified == false) | "\(.id)  \(.severity)  \(.title)"' \
   docs/03-data/findings-register.json
```

**Finding counts by type and severity:**

```bash
jq '.meta.counts_by_type, .meta.counts_by_severity' docs/03-data/findings-register.json
```

**Which collections does one page write to?**

```bash
jq -r '[.actions[] | select(.page_id == "wallets") | .writes_to[]] | unique | .[]' \
   docs/03-data/actions-catalog.json
```

**Destructive actions with no confirmation step:**

```bash
jq -r '.actions[] | select(.destructive and (.confirmed | not))
       | "\(.handler)  L\(.line)  \(.page_id // "—")"' \
   docs/03-data/actions-catalog.json
```

**Every KPI whose value is hardcoded rather than computed:**

```bash
jq -r '.modules[] | .id as $m | .kpis[]? | select(.source | test("hardcode"; "i"))
       | "\($m): \(.name)  L\(.line)"' \
   docs/03-data/system-inventory.json docs/03-data/modules-detail.json 2>/dev/null
```

**Pages you cannot reach from the sidebar, and how they open instead:**

```bash
jq -r '.navigation.orphan_pages[] | "\(.page_id)  ←  \(.reached_via // "NOTHING — unreachable")"' \
   docs/03-data/system-inventory.json
```

**Entities with no seeded demo records** (empty at load — every list on them renders its empty state):

```bash
jq -r '.entities[] | select(.seed_count == 0) | .db_collection' docs/03-data/entities.json
```

**Join a module to its findings:**

```bash
jq -r --arg m 12b-driver-wallets \
   '.findings[] | select(.module == $m) | "\(.id) [\(.severity)] \(.title)"' \
   docs/03-data/findings-register.json
```

**Validate every file parses** (should print five `ok` lines and nothing else):

```bash
for f in docs/03-data/*.json; do
  node -e "JSON.parse(require('fs').readFileSync('$f','utf8'))" && echo "ok  $f"
done
```

## Data-quality caveats

Two fields do **not** mean what a naive query would assume. Read this before
drawing conclusions from a query.

### 1. `confirmed` is under-populated — do not query it

`actions-catalog.json` distribution across all 414 actions:

```
confirmed=false : 412
confirmed=true  :   2
```

That is not the reality. `docs/01-modules/00b-global-ui-systems.md` documents
**88 gated actions across four separate mechanisms** (`installActionGates`,
`GATE_SPECS`, `GATE_SWEEP`, standalone `guardAction`). The extractor appears to
have detected only inline confirmation calls, not registry membership — the
registries bind gates to handler *names* at runtime, which a static per-function
read does not see.

Spot-check: `commitWalletAdjust` is registry-gated in source but appears as
`confirmed: false`.

**Consequence.** A query like *"money-moving actions with no confirmation"*
returns all 40 and is meaningless. For confirmation coverage use
`00b-global-ui-systems.md` §4 (the gate registry), not this field.

The `permission_gate` and `audit_action_key` fields **are** reliable — they are
read from `requirePerm(...)` and `logAction(...)` calls in the function body.

### 2. The catalog is not a complete function census

`payDriver` — verified at `L7023`, gated on `process_payouts`, and the function
that actually moves driver payout money — **is absent from
`actions-catalog.json`.**

The catalog was built from actions bound to UI elements (`onclick` and friends).
`payDriver` is called from `executePayout` rather than bound directly to a
control, so it never entered the extraction. Other internal money functions
reached only through wrappers are likely missing for the same reason.

**Consequence.** Treat `actions-catalog.json` as *"actions reachable from a UI
control"*, not *"all actions"*. For a complete function census use
`docs/00-index/GROUND-TRUTH-INVENTORY.md` (1,039 declared functions) and
`docs/03-data/DATA-MODEL.md` (per-collection reader/writer lists).

### Queries that ARE sound

```bash
# money-moving actions with no permission gate  → 7
node -e "const a=require('./actions-catalog.json'); \
  console.log(a.actions.filter(x=>x.moves_money&&!x.permission_gate).length)"

# destructive actions with no permission gate   → 8
node -e "const a=require('./actions-catalog.json'); \
  console.log(a.actions.filter(x=>x.destructive&&!x.permission_gate).length)"

# findings by severity  → critical 16 / high 89 / medium 279 / low 261
node -e "const f=require('./findings-register.json'); const s={}; \
  f.findings.forEach(x=>s[x.severity]=(s[x.severity]||0)+1); console.log(s)"
```

Each of these reads a field populated directly from source text, and each was
verified against the file. The caveat above applies only to `confirmed` and to
completeness of the action list.
